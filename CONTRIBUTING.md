# Как устроена разработка

## Ветки

| Ветка | Что в ней | Кто пишет |
|---|---|---|
| `main` | проверенный код, из неё выпускаются релизы | только слияния из `unstable` |
| `unstable` | текущая разработка, может быть сломана | сюда вливаются ветки задач |
| `feature/*`, `fix/*` | отдельные задачи, живут недолго | автор задачи |

Поток всегда один: `feature/*` → `unstable` → `main`. Обратное направление
существует только для исправлений, сделанных прямо на `main` (см. ниже).

Названием `unstable` проект следует традиции Debian: это не «черновик», а
ветка, где код собран и проходит тесты, но ещё не проверен вживую.

## Три правила, без которых схема разваливается

### 1. Слияние `unstable` → `main` только обычным коммитом слияния

**Никогда не используйте Squash merge для этого слияния.** Squash создаёт на
`main` новый коммит, которого нет в `unstable`. Ветки расходятся навсегда,
и каждое следующее слияние приносит конфликты в уже слитом коде.

Для веток задач в `unstable` squash, наоборот, удобен: он превращает десяток
коммитов вида «fix typo» в один осмысленный.

Итого:

- `feature/*` → `unstable`: **Squash and merge**;
- `unstable` → `main`: **Create a merge commit**.

### 2. Исправление на `main` немедленно возвращается в `unstable`

Если срочный фикс сделан прямо на `main`, сразу влейте `main` в `unstable`:

```
git checkout unstable
git merge main
git push
```

Иначе следующее слияние `unstable` → `main` откатит исправление: в
`unstable` этих изменений нет, и слияние честно вернёт старое состояние.

### 3. Теги ставятся только на `main`

Релизный workflow проверяет это и отказывается собирать релиз с тега,
которого нет в истории `main`. Иначе непроверенная сборка вышла бы под
видом релиза.

## Обычный цикл

```
# начать задачу
git checkout unstable && git pull
git checkout -b feature/modrinth-plugins

# ... работа, коммиты ...
git push -u origin feature/modrinth-plugins
# → Pull Request с базой unstable, squash merge после зелёного CI

# проверить вживую
# сборки под все платформы лежат в артефактах прогона Snapshot
# на вкладке Actions

# выпустить
# → Pull Request unstable → main, обычный merge commit
git checkout main && git pull
git tag -a v0.2.0 -m "v0.2.0"
git push origin v0.2.0
# → workflow Release соберёт, подпишет и опубликует
```

## Что нужно настроить в репозитории

Настройки GitHub, которые файлами не задаются:

1. **Создать ветку `unstable`** от `main`.
2. **Default branch оставить `main`.** Тот, кто клонирует репозиторий, должен
   получать проверенный код. Побочный эффект: новые Pull Request по умолчанию
   открываются в `main`, поэтому база меняется вручную — об этом напоминает
   шаблон PR.
3. **Branch protection на `main`:** запретить прямой push, требовать Pull
   Request и зелёный CI.
4. **Branch protection на `unstable`:** только требование зелёного CI. Держать
   здесь строгие правила смысла нет, иначе ветка перестанет быть местом для
   экспериментов.
5. **Allowed merge methods:** оставить включёнными и squash, и merge commit —
   они нужны для разных слияний (см. правило 1).

## Версии в снапшотах

Сборки с `unstable` получают версию вида `unstable-42-a1b2c3d`, где `42` —
номер прогона, а `a1b2c3d` — коммит. Команда `izba version` показывает её,
так что по выводу всегда понятно, что именно проверялось.

## Проверки перед Pull Request

Требуется Go 1.24 или новее: более старые компиляторы не пишут LC_UUID в
Mach-O, и собранное ими не запускается на macOS 26.

```
make check
```

Прогоняет тесты с детектором гонок, `go vet` и проверку форматирования — то
же самое, что делает CI.

## Что проверить вживую перед слиянием в `main`

Автоматические тесты не покрывают сеть и запуск JVM: обращений к Mojang,
PaperMC и Adoptium в тестах нет, они работают на замоканных ответах. Поэтому
перед выпуском нужен ручной прогон:

- `izba init && izba up` на Linux и на Windows;
- распаковка архива Temurin прошла успешно;
- сервер дошёл до строки готовности;
- `Ctrl+C` остановил сервер с сохранением мира;
- повторный `izba up` не скачивает ничего заново.
